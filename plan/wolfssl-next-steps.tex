\section{What the received documents settle}

The wolfCrypt v5.2.1 FIPS User Guide (doc v1.3, 2026-03-05) and the Windows
\code{user\_settings.h} answer most of our open questions:

\begin{enumerate}
  \item \textbf{Our Windows OE is already in the User Guide.} Section 2.2.45
        (OE49) documents Windows 11 Pro on Lenovo ThinkPad T14 with Intel
        i7-1260P, built with the supplied \code{user\_settings.h}
        (\code{HAVE\_FIPS\_VERSION 5 / MINOR 2 / PATCH 1}). Only certificate
        publication remains.
  \item \textbf{Toolchain pin.} OE49 lists Visual Studio 2026 as compiler,
        linker, assembler, and debugger. The UG states a module compiled with a
        toolchain not on the list is not FIPS validated until retested. Our
        Windows build must use Visual Studio 2026.
  \item \textbf{No PAA on OE49.} The UG marks OE49 ``no PAA only'' and warns
        PAA is not allowed without retesting. We build without
        \code{WOLFSSL\_AESNI}.
  \item \textbf{Windows integrity-hash flow.} The fips-hash.sh equivalent on
        Windows is documented: build, run once, read the hash from the FIPS
        callback, set it via \code{WOLFCRYPT\_FIPS\_CORE\_HASH\_VALUE} or
        \code{verifyCore[]}, rebuild.
  \item \textbf{Our entropy design is the documented pattern.} UG section 6
        instructs developers without RDSEED to provide their own seeding
        function from a strong entropy source, and the API table describes
        \code{wc\_SetSeed\_Cb\_fips} as the hook for an external entropy source
        that ``may be SP800-90B or may not''. The Lightrider provider (OS
        kernel entropy plus RCT/APT verification, fail-closed) fits this
        exactly, under the caveat ``no assurance of the minimum strength of
        generated keys''.
  \item \textbf{Azure Linux recipe.} UG 2.2.38 (OE36) gives the exact
        configure/make/fips-hash flow and toolchain (gcc 13.3) for the tested
        cloud OE.
\end{enumerate}

\section{Our response to wolfSSL}

\begin{quote}
\small
Subject: RE: FIPS \#4718: User Guide received, remaining items

Thank you. The v5.2.1 User Guide and Windows \code{user\_settings.h} answer our
build questions, including the OE49 recipe, the Visual Studio 2026 toolchain,
the no-PAA requirement, and the Windows integrity-hash flow. Four items remain:

1. Publication. Please notify us when OE49 (Windows 11 Pro, i7-1260P) and OE36
(Azure Ubuntu 24.04 on Docker) appear on the published \#4718 certificate and
security policy, and share any expected CMVP timeframe. Until then we ship
Windows with validation status ``pending publication''.

2. Entropy confirmation. Per UG section 6 we register our own generate-seed
callback through \code{wc\_SetSeed\_Cb}: it reads OS kernel entropy
(\code{getrandom} on Linux, \code{BCryptGenRandom} on Windows) and applies our
own SP 800-90B-style repetition-count and adaptive-proportion checks before
returning, failing closed. We document it as the CO-registered external seed
source under legacy IG 9.3.A with no ESV claim. Please confirm this raises no
concern.

3. Authenticode. Does signing the DLL or the installer interact in any way with
the in-core integrity check we should plan for?

4. Order Form. We would like to paper: (a) Veloce as the named Program under
section 3 (a PQC SDK exposing crypto services through a local agent, not a
linkable crypto library); (b) commercial coverage for compiling the
ML-KEM/ML-DSA sources from the public v5.9.2-stable tree as a separate
non-FIPS provider, since the commercial bundle strips SHAKE; and (c) budget and
timing for the FIPS v7 PQ-FS upgrade.
\end{quote}
