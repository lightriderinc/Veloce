\section{Executive Summary}\label{sec:exec}

Veloce is Lightrider's V1 PQC SDK. It comprises a cryptographic discovery component
(qSearch) and a FIPS 140-3 crypto core with a validated entropy pipeline. Both operate
fully offline; an optional EMS connection provides fleet telemetry and user-controlled
cloud entropy.

\textbf{Document organization.} This document is the implementation specification for
Veloce V1 and is sufficient for reimplementation on its own. Sections
\ref{sec:arch}--\ref{sec:ems} define the components, Section~\ref{sec:api} the public
API and deliverables, Section~\ref{sec:security} the security controls,
Section~\ref{sec:gates} the acceptance tests, Section~\ref{sec:schedule} the build order
with a component-to-repository map, and the appendices the exact build commands.

\textbf{Implementation snapshot (2026-08-27).} The checked-in implementation contains
the C++ agent, pure-Python client, Rust CLI, native Rust qSearch source/system scanner,
CBOM outputs, the Veloce Desktop application (local web UI: security dashboard +
click-to-scan qSearch), Windows/macOS desktop build paths, and a 42-test gate battery.
The current source scanner is a single-threaded recursive literal-pattern engine, not yet
the parallel collector design described as the target below. Hybrid-TLS policy selection
exists, but the TLS data plane, native Windows FIPS runtime validation, dependency/PCAP
collectors, and the EMS network client are not implemented. This distinction is
normative: target requirements must not be reported as delivered functionality.

\textbf{Vendor response snapshot (2026-08-27).} wolfSSL confirmed in writing:
(1) Windows FIPS supports \emph{DLL builds only} (the bundled README's static-library
statement is a legacy error, correction in wolfSSL PR \#11142); build configurations are
\code{DLL Debug | x64} / \code{DLL Release | x64} in \code{WIN10/wolfssl-fips.sln}.
(2) The exact v5.2.1 \code{user\_settings.h} is supplied
(\code{HAVE\_FIPS\_VERSION\_MAJOR 5, MINOR 2, PATCH 1}).
(3) CAVP/CMVP testing for the Windows 11 Pro / Intel i7-1260P (Lenovo ThinkPad T14) OE
and an Azure Linux OE (Ubuntu 24.04 on Docker 28.5 / Hyper-V, Xeon Platinum 8272CL) is
\emph{completed, awaiting publication} on certificate \#4718 and its security policy.
(4) The module makes no entropy claim; the CO registers a custom generate-seed callback
via \code{wc\_SetSeed\_Cb()} (wolfSSL FIPS FAQ \S2), and the module falls under
\emph{legacy} IG~9.3.A (validated before 2026-01-01), exempt from the current ESV
verbiage. (5) wolfEntropy \emph{was never tested with v5.2.1} and wolfSSL recommends not
using it with the legacy module; ESV \#E335 belongs to the separate v6.0.0 module, and
the v5.2.4 upgrade path is roughly a year out as a new certificate. (6) The wolfCrypt
FIPS User Guide / COGM is now on hand and governs allowed build settings. These answers
close the S0 vendor items; the only remaining external dependency for the Windows
validated-deployment claim is CMVP publication of the tested OE rows.

\subsection*{The two pillars}
\begin{description}[style=nextline]
  \item[Pillar A: qSearch (cryptographic search).] A Rust-based discovery engine with
  a native literal-pattern and PEM-certificate collector today, with replaceable
  dependency and network collectors planned. It finds RSA, DH, ECDH, ECDSA and other
  quantum-vulnerable indicators in source code and certificates, and emits JSON, CSV,
  CycloneDX CBOM, and
  OMB M-23-02 inventory fields. Lightrider owns the normalization, correlation,
  classification, CBOM generation, risk scoring, and reporting layers.
  \item[Pillar B: Entropy generator and FIPS crypto core.] A native C++17 agent embedding
  the wolfCrypt FIPS 140-3 validated module (CMVP cert \#4718) whose SP~800-90A Hash\_DRBG
  is seeded only by the Lightrider local entropy provider: a custom generate-seed callback
  (\code{wc\_SetSeed\_Cb()}, per wolfSSL FIPS FAQ \S2) drawing OS kernel entropy
  (\code{getrandom()} on Linux, \code{BCryptGenRandom} on Windows) and verifying every
  seed block in-process with SP~800-90B-style RCT/APT health tests, fail-closed. No ESV
  certificate is claimed; the module makes no entropy claim and legacy IG~9.3.A applies
  (vendor-confirmed). The agent provides ML-KEM-768 key establishment and ML-DSA
  signatures, consumed from a pure-Python SDK over an authenticated local IPC channel.
  Hybrid TLS 1.3 policy selection is present; the sample handshake/data plane remains a
  G3 deliverable.
\end{description}

  secure if either component holds. \\

Module boundary & The exact code covered by a FIPS certificate; anything outside it
  carries no validation claim. \\
OE & Operational environment: the specific operating system and hardware a validation
  was tested on. \\
Entropy & Unpredictable data used to seed random-number generation; the root of all key
  security. \\
ESV & NIST Entropy Source Validation: certifies an entropy source under SP~800-90B. \\
DRBG & Deterministic random bit generator: expands a small entropy seed into unlimited
  random output (SP~800-90A). \\
RCT / APT & The two continuous entropy health tests (repetition count, adaptive
  proportion) required by SP~800-90B. \\
KAT / CAST & Known-answer test / conditional algorithm self-test: fixed-input checks a
  FIPS module runs on its own algorithms. \\
CBOM / SBOM & Cryptography / software bill of materials: an inventory of where and how
  cryptography (or software) is used. \\
Collector & A replaceable tool qSearch uses to gather raw evidence (source scan,
  certificate scan, network capture). \\
Correlate & Merge findings from different collectors that refer to the same asset. \\
Remediation & Changing or replacing vulnerable cryptography; V1 discovers and reports
  only. \\
IPC & Inter-process communication: the authenticated local channel between the Python
  SDK/CLI and the agent. \\
EMS & Lightrider's cloud platform (\code{light-rider-platform}) for fleet telemetry and
  cloud entropy. \\
M-23-02 & The U.S.\ federal memorandum requiring agencies to inventory quantum-vulnerable
  cryptography. \\

\section{System Architecture}\label{sec:arch}

One native agent owns all keys, entropy, and FIPS state. Python and the CLI are thin,
crypto-free IPC clients. qSearch is a separate Rust binary outside the FIPS boundary that
shares only the CBOM data model with the SDK. EMS is reachable only from the agent, only
when enabled.

\subsection{Detection targets and outputs}
V1 prioritizes \emph{active} cryptography: key establishment, encrypted connections,
digital signatures, authentication, code/firmware signing. Classification flags RSA, DH,
ECDH, ECDSA (and small-key symmetric use) as quantum-vulnerable; ML-KEM/ML-DSA usage is
recognized and reported as PQC-ready.

Outputs: \textbf{JSON} (canonical), \textbf{CSV}, \textbf{CycloneDX CBOM},
\textbf{M-23-02 inventory fields}, \textbf{executive summary}, and \textbf{SDK runtime
validation records} (the Veloce agent's own CBOM self-report merges into the same store).

\subsection{Coverage assurance and outlier names}
No finite keyword list can guarantee discovery of every crypto wrapper, alias, generated
binding, renamed module, or proprietary API. qSearch therefore treats keyword matches as
evidence, not proof, and uses a layered coverage model:
\begin{enumerate}
  \item Curated rules include canonical standards, historical names (for example Kyber
        and Dilithium), vendor APIs, language bindings, protocol groups, OIDs, imports,
        package names, and configuration keys. Rules move to a versioned external
        JSON/TOML file with rule identifier, aliases, classification, risk, source, and
        regression fixture.
  \item Structural collectors examine certificates, dependency manifests, linked/loaded
        libraries, symbols, processes, and protocol observations. These catch modules
        whose application-facing name does not contain a known algorithm keyword.
  \item Every rule has positive, negative, alias, comment/test, and boundary fixtures.
        Controlled corpora measure precision, recall, false positives, and explicit blind
        spots. Unknown providers are reported as context for analyst review, never silently
        classified as safe.
  \item Customer/vendor dictionaries may add organization-specific wrapper and product
        names without rebuilding qSearch. Signed rule-pack versions are recorded in every
        run log and CBOM record.
\end{enumerate}

\subsection{Optional AI triage}
AI is an enrichment stage after deterministic collection; it is never the sole source of
a CBOM fact. qSearch batches findings and, only with explicit tenant opt-in, submits the
minimum necessary context (rule ID, path token, matched line and a bounded surrounding
window) to a Lightrider AI gateway. The gateway may classify active code versus comments,
tests, examples, or wrappers; suggest aliases; explain risk; and propose remediation. The
original match, file/line evidence, model/version, prompt-policy version, confidence, and
human disposition remain in the audit record.

The model-provider credential is stored once in Lightrider's server-side secret manager
and is never shipped in qSearch, a wheel, a CLI flag, a repository, or a customer report.
Customers authenticate to Lightrider with a scoped tenant credential; the gateway attaches
the provider credential and applies quotas, redaction, retention, and audit policy. Calls
are batched per scan/chunk, not made once per keyword. A bring-your-own-key mode and a
fully local/offline model are optional deployment profiles. AI failure, denial, or timeout
must not block deterministic scanning or alter the zero-network guarantee when EMS/AI is
disabled.

\subsection{Performance approach}
Current implementation: a single-threaded depth-first \code{read\_dir} walk loads each
readable file up to 4 MiB as UTF-8, then applies every literal pattern to every line. It
does not use an index, AST, memory mapping, Aho--Corasick, or incremental hashes.

Target upgrade: parallel ignore-aware walking; one compiled Aho--Corasick/regex-set pass;
bounded streaming; and incremental re-scan keyed on file hashes. AI runs only on the much
smaller finding set. Benchmarks and false-positive/blind-spot reporting are release gates
(Section~\ref{sec:gates}).

\section{Pillar B: Entropy Generator and FIPS Crypto Core}\label{sec:core}

The crypto core consists of a verified local entropy provider feeding a validated DRBG,
with PQC and TLS services above it. All failure modes are fail-closed.

\subsection{Entropy pipeline}

\textbf{Wiring.} The module itself makes no entropy claim (\#4718 SP \S11.1,
vendor-confirmed); its security policy requires the crypto officer to register an
external seed source. After loading the module and checking
\code{wolfCrypt\_GetStatus\_fips()}, the agent registers the \emph{Lightrider
generate-seed callback} with \code{wc\_SetSeed\_Cb()} --- the mechanism wolfSSL's FIPS
FAQ \S2 prescribes for custom seeding --- and instantiates the FIPS DRBG with
\code{wc\_InitRng()}. The callback acquires seed material from the OS kernel entropy
interface, runs the Lightrider RCT/APT verification over every block, and returns it
only on pass; any acquisition or health-test failure returns an error, and because the
FIPS build defines \code{WC\_RNG\_SEED\_CB}, the DRBG then refuses to instantiate or
reseed --- there is no silent fallback path. wolfEntropy is not used: wolfSSL confirmed
on 2026-08-27 that it was never tested with module v5.2.1 and recommends against pairing
it with the legacy module. The agent exposes
\code{FipsCore::randomBytes()} as a callback to the separate PQC provider: ML-KEM keygen
requests 64 bytes; ML-KEM encapsulation, ML-DSA keygen, and hedged ML-DSA signing request
32 bytes each. Applications never supply or retrieve raw entropy.

\textbf{Fail-closed policy.} If entropy initialization, a health test (RCT/APT), or a
reseed fails, the agent transitions to a degraded state: all key generation, signing,
encapsulation, and TLS handshakes are refused; \code{health()} and the validation-status
API report the failure; an event-log entry and (if enabled) an EMS alert are emitted.
There is no API that returns raw entropy, and entropy is never sent to EMS.

\textbf{Certification position (resolved 2026-08-27).} No ESV certificate applies to
this module and none is claimed: wolfSSL confirmed ESV \#E335 belongs to their separate
v6.0.0 module (currently ``Pending Resubmission''), that wolfEntropy was never tested
with v5.2.1, and that v5.2.4 --- the first version designed for ESV-mode seeding --- is
about a year from certification as a \emph{new} certificate. Module \#4718 was validated
before 2026-01-01 and therefore falls under \emph{legacy} IG~9.3.A, which permits an
external documented seed source without an attached ESV validation. Veloce's compliance
position is exactly that: the module's own certificate plus a documented, health-tested
external seed source, reported honestly in \code{validation\_status()} as
\code{entropy\_esv\_certified:\ false}, \code{entropy\_verified\_local:\ true}. The
Lightrider RCT/APT layer is engineering assurance and is never represented as an ESV
credit. Per wolfSSL: ``testing is the only confidence when it comes to FIPS''; the
verification layer plus the gate battery is that testing.

\textbf{Entropy providers.} V1 ships exactly one seed provider: the Lightrider local
entropy provider (OS kernel entropy, verified per block). No hardware entropy is
integrated in V1. Two quantum-entropy integrations follow post-V1: the
\textbf{Quantropi} quantum-entropy service (QiSpace SEQUR), delivered over the network
through the EMS cloud-entropy channel as DRBG additional input
(Section~\ref{sec:cloud-entropy}); and the IDQ Quantis QRNG as a local alternate seed
source for Quantum Light deployments.
\code{list\_entropy\_providers()} enumerates providers, so new sources are added without
API change.

\subsection{FIPS module integration}
\begin{itemize}
  \item Module: wolfCrypt FIPS 140-3 v5.2.1, CMVP cert \#4718; library wolfSSL 5.9.2.
        Built with \code{-{}-enable-fips=v5} via autotools (CMake is not FIPS-capable in
        this tree). Loaded as a shared library / DLL, never statically linked; protected
        module files are never renamed, patched, or recompiled without wolfSSL approval.
  \item In-core integrity: HMAC-SHA256 check; build flow is
        \code{configure} $\rightarrow$ \code{make} $\rightarrow$ \code{./fips-hash.sh}
        $\rightarrow$ \code{make} $\rightarrow$ \code{testwolfcrypt} (Appendix~\ref{app:build}).
  \item Self-tests: power-on self-test at load plus conditional algorithm self-tests
        (CASTs) for AES-CBC/GCM, HMAC-SHA-1/2/3, DRBG, RSA sign, ECDSA, ECC-CDH, DH-Z,
        and the TLS 1.2/1.3/SSH KDFs. The SDK's \code{run\_fips\_self\_tests()} calls
        \code{wc\_RunAllCast\_fips()}, and status is read from
        \code{wolfCrypt\_GetStatus\_fips()}.
  \item Record for every build: DLL/so hash, source version, build settings, compiler,
        FIPS certificate, entropy provider status, operating environment (feeds the
        CBOM).
  \item Windows FIPS build (vendor-confirmed 2026-08-27): \textbf{only DLL builds are

  \item OE status (vendor-confirmed 2026-08-27): CAVP/CMVP testing is \emph{completed,

\subsection{PQC provider outside the FIPS boundary}\label{sec:pqc-boundary}
The \#4718 boundary contains classical algorithms only, and this FIPS build strips the
SHAKE/XOF primitives that ML-KEM and ML-DSA require, so \textbf{PQC cannot link inside
the v5 FIPS build}. V1 therefore compiles the wolfSSL ML-KEM/ML-DSA sources (FIPS 203/204,
with fault-hardening flags) as a separate \emph{PQC provider} library beside the boundary,
drawing all randomness from the FIPS DRBG via the \code{*WithRandom} APIs.

\begin{itemize}
  \item Validation status reports each fact separately (no generic \code{FIPS=True}):
        module validated + cert number; \code{entropy\_esv\_certified:\ false} +
        \code{entropy\_verified\_local:\ true}; PQC algorithm
        and its validation status; \code{pqc\_inside\_fips\_boundary:\ false}; OE;
        self-test results. Values come from the installed module, never hardcoded.
  \item \dep{Track wolfSSL's FIPS v7 ``PQ-FS'' submission (boundary wrappers for ML-KEM,
        ML-DSA, LMS, XMSS, SLH-DSA + SHA-512 DRBG). Migrating to v7 flips
        \code{pqc\_inside\_fips\_boundary} to true with no API change; the provider
        interface is designed for that swap.}
  \item CAVP/ACVTS testing of the PQC provider (known-answer + interface tests) is planned
        so the CBOM can cite algorithm-level evidence even before v7.
        \open{Choose ACVTS scope and lab.}
\end{itemize}

\subsection{Hybrid TLS 1.3}
Sample client and server negotiate a wolfSSL-supported hybrid group. Candidates:
\code{X25519MLKEM768} (default), \code{SecP256r1MLKEM768}, \code{SecP384r1MLKEM1024}.
The public API accepts a \emph{policy profile}, never raw algorithm strings:

\begin{quote}
\code{session = veloce.tls.connect(host=..., port=443, policy="LIGHTRIDER\_PQC\_TRANSITION")}
\end{quote}

Performance is verified by measurement. Using

\subsection{Modes and configuration}
\begin{quote}
\code{ems:\ \{ mode:\ disabled \}} \hfill or \hfill

\end{quote}

\begin{small}
\begin{tabularx}{\textwidth}{@{}lL@{}}
\toprule
\textbf{EMS may receive} & Agent health; SDK and module versions; CBOM records; policy
  identifiers; self-test status; entropy-provider status; non-sensitive operational

\textbf{Endpoint contract (resolved from \code{light-rider-platform}).} The EMS
data plane is the \code{ems-egress} service: REST on \code{:7081}
(\code{POST /v1/entropy/request}, 1--65\,536 bytes per call; \code{GET /v1/sources};
\code{GET /v1/entropy/pools}; \code{GET /v1/pubkey};
\code{GET /v1/receipts/:request\_id}), a WebSocket stream
(\code{GET /v1/entropy/stream}) with parameters \code{policy} and
\code{bytes\_per\_tick} (default 64, clamped 1--4096) on a fixed 100\,ms tick, and a
QUIC lane (\code{:7082}, ALPN \code{lr-qstream}) that already negotiates hybrid
\code{X25519MLKEM768}. Wire schemas are fixed by
\code{proto/entropy.proto} (\code{EntropyRequest/Response}, \code{EntropyReceipt},
\code{HealthSnapshot}, \code{SourceSelectionPolicy}). Every response carries a
\emph{signed receipt} (Ed25519 today; ML-DSA-65 / MASQ-DS paths exist) containing the
contributing sources, pool, extractor algorithm, SP~800-90B health snapshot (RCT/APT
pass, bit balance, Shannon estimate, chi-square p-value, quality score 0--100),
DRBG algorithm and reseed id, and a nanosecond timestamp; \code{raw\_entropy\_stored}
is always false. Authentication is a per-device Bearer API key issued by the
\code{ems-admin} control plane; entitlement tiers (Free/Pro/Enterprise) gate the pools
(\code{pool\_fastest}, \code{pool\_highest\_quality}, \code{pool\_quantum\_verified}).
The agent is the only Veloce component that opens the connection, verifies the receipt
signature against the pinned EMS public key, and enforces freshness before any use.
mTLS device enrollment remains the target transport hardening once EMS supports it.

\subsection{User-controllable cloud entropy (V1 addition)}\label{sec:cloud-entropy}
EMS may deliver entropy \emph{to} devices; devices never send entropy to EMS.

\textbf{Design.}
\begin{enumerate}
  \item The agent (when \code{entropy\_mixin:\ on}) periodically fetches an authenticated,
        freshness-checked entropy packet from EMS over mTLS.
  \item The packet is injected into the wolfCrypt DRBG as SP~800-90A
        \emph{additional input} on reseed/generate: it is cryptographically mixed in but
        contributes \emph{zero} to the credited entropy claim. The local Lightrider
        entropy provider remains the sole seed. The FIPS certificate claims are
        unaffected.
  \item User control: enable/disable per config or at runtime via the SDK
        (\code{set\_entropy\_mixin(...)}); state is visible in \code{health()},
        \code{list\_entropy\_providers()}, validation status, and the CBOM
        (\code{cloud\_entropy\_mixin:\ on/off}).
  \item Fail-safe: EMS unreachable, stale, or malformed packets $\Rightarrow$ mix-in is
        skipped and local operation continues untouched; a status flag records the last
        successful mix-in. Cloud entropy can never block or degrade local crypto.
\end{enumerate}
Post-V1, the same delivery channel carries quantum-sourced entropy: the Quantropi
quantum-entropy service (QiSpace SEQUR) as the EMS upstream source (the platform's
\code{qispace} collector already ingests TQRND in 4096-byte blocks), and Quantum Light
QPU-derived entropy.

\subsection{Desktop UI: entropy specs and cloud-EMS control (V1 addition)}
\label{sec:entropy-ui}

The Veloce Desktop application (\code{desktop/}, a local web UI served only on
\code{127.0.0.1} and backed exclusively by the SDK/IPC --- it never touches wolfCrypt)
gains an \textbf{Entropy} page beside the existing security dashboard and qSearch pages.
The page has exactly two jobs:

\begin{enumerate}
  \item \textbf{Show the live entropy streaming specs.} One table, populated from
        \code{list\_entropy\_providers()} and \code{health()}, never hardcoded:
        provider name and type (\code{lightrider-local}, OS kernel interface); DRBG
        (Hash\_DRBG SHA-256, 256-bit strength, reseed interval); health-test status and
        counters (RCT cutoff 31, APT 325/512, blocks verified, failures --- always zero
        or the agent is degraded); last seed/reseed time; and, when the mix-in is on,
        the last EMS receipt summary (pool, contributing sources, quality score,
        signature status, freshness age, bytes per tick). Raw entropy values are never
        displayed or exposed.
  \item \textbf{One switch: cloud EMS on/off.} A single toggle wired to
        \code{set\_entropy\_mixin(...)} plus an endpoint/API-key field (stored in the
        agent config, not the browser). Turning it on never changes the FIPS story ---
        the panel states in fixed text that cloud entropy is additional input with zero
        credited entropy and that the local provider remains the sole seed. Turning it
        off is immediate and is the default state. The toggle state is mirrored in
        \code{health()}, \code{validation\_status()}, and the CBOM
        (\code{cloud\_entropy\_mixin:\ on/off}).
\end{enumerate}

Acceptance (G3): the page renders correct specs with EMS disabled and no network
traffic; enabling the toggle starts authenticated fetches and updates the receipt
summary; killing EMS mid-session flips the mix-in status to \code{stale/skipped} while
all local crypto continues; the toggle round-trips through config restart.

        unit; \code{veloce status} or the desktop app confirms the state.
  \item \textbf{Python:} \code{pip install veloce\_pqc} for the SDK; it requires a
        running agent and contains no cryptography.
\end{itemize}

First run always shows the same three facts, from live status only: FIPS module
(cert \#4718 + self-test result), entropy (local provider verified, fail-closed), and
PQC provider (beside boundary). Enabling EMS cloud support is one action from the
desktop app's entropy page (Section~\ref{sec:entropy-ui}) or one config line; it is
never required for any local function. Every install is reproducible from the release
manifest: each artifact carries SHA-256 checksums, the SBOM/CBOM, tested OS/CPU, and
gate report (Section~7.3), and the build recipes in Appendix~\ref{app:build} regenerate
byte-comparable libraries from the same bundle and flags.

\subsection{Platform-separated development and release layout}
All operating systems remain in one repository and share protocol, algorithm, report,
and conformance-test definitions. OS-specific code is isolated behind transport, library
loader, service, system-discovery, and packaging interfaces; platform conditionals must
not spread through cryptographic policy code. The target source layout is:

\begin{quote}
\code{platform/linux/}\quad Unix socket/peer credentials, \code{dlopen}, systemd,
Linux collectors\\
\code{platform/windows/}\quad named pipe/ACL, \code{LoadLibraryExW}, Windows service,
Windows collectors\\
\code{platform/macos/}\quad local IPC/peer authorization, \code{dylib}, launchd,
Keychain/macOS collectors\\
\code{core/}, \code{ipc/}, \code{python/}, \code{qsearch/}\quad shared behavior and
schemas\\
\code{installer/\{linux,windows,macos\}/}\quad platform package inputs
\end{quote}

The existing Linux implementation remains in \code{agent/}, \code{cli/}, and
\code{qsearch/src/system.rs} until the adapters are extracted; empty or planned platform
directories do not imply support. Releases are assembled into explicit targets, never a
mixed archive:

\begin{quote}
\code{release/<version>/linux/x86\_64/}\quad tar/deb/rpm, ELF binaries and \code{.so}s\\
\code{release/<version>/windows/x86\_64/}\quad signed MSI, PE binaries and DLLs\\
\code{release/<version>/macos/\{x86\_64,arm64\}/}\quad signed/notarized package and
\code{.dylib}s\\
\code{release/<version>/common/}\quad protocol/docs plus only genuinely portable files
\end{quote}

Each target carries its own manifest, SHA-256 checksums, SBOM/CBOM, tested OS/CPU,
validation claims, known limitations, and gate report. The current
\code{scripts/make\_release.sh} produces Linux x86-64 only; Windows and macOS release
folders must not be emitted until their gates pass.

\section{Build Recipes}\label{app:build}

\subsection*{Linux FIPS module (bundle on hand)}
\begin{quote}
\code{cd vendor/wolfssl}\\
\code{./configure -{}-enable-fips=v5}\\
\code{make}\\
\code{./fips-hash.sh}\quad\emph{\small(updates the in-core HMAC-SHA256 verify hash)}\\
\code{make}\\
\code{./wolfcrypt/test/testwolfcrypt}\quad\emph{\small(must report all tests passed)}
\end{quote}
Notes: autotools is the only FIPS-capable build path in this tree; \code{-{}-enable-fips}
also turns on reproducible builds. \code{-{}-enable-wolfEntropy} is \emph{removed}:
wolfSSL confirmed 2026-08-27 that wolfEntropy was never tested with v5.2.1 and is not to
be used with the legacy module; seeding is the Lightrider callback registered at runtime.
Check the final flag set against the wolfCrypt FIPS User Guide / COGM (on hand). Record
DLL/so SHA-256, source version, compiler, and flags into the CBOM store at build time.

\subsection*{PQC provider (beside boundary)}
Separate non-FIPS build of the same wolfSSL tree (or standalone compilation of
\code{wc\_mlkem.*} and \code{wc\_mldsa.*} with SHAKE enabled), configured with
\code{-{}-enable-mlkem -{}-enable-mldsa} plus the fault-hardening flags
\code{WC\_MLKEM\_FAULT\_HARDEN} and \code{WC\_MLDSA\_FAULT\_HARDEN}; randomness supplied
exclusively from the FIPS DRBG via the \code{*WithRandom} APIs; distinct library name and
symbol namespace so the two builds can never be confused at load time.

\subsection*{Windows (configuration vendor-confirmed 2026-08-27)}
Open the wolfSSL-provided \code{IDE/WIN10} FIPS solution (\code{wolfssl-fips.sln}) in
Visual Studio and select build configuration \code{DLL Debug | x64} or
\code{DLL Release | x64}. Only DLL builds are supported with FIPS; the README's
static-library instruction is a legacy copy/paste error being corrected in wolfSSL
PR \#11142. Use the vendor-supplied v5.2.1 \code{user\_settings.h}
(\code{HAVE\_FIPS\_VERSION\_MAJOR 5}, \code{HAVE\_FIPS\_VERSION\_MINOR 2},
\code{HAVE\_FIPS\_VERSION\_PATCH 1}) and the documented in-core integrity linker
settings, then run the same hash-verify-record flow (\code{fips-hash} equivalent +
\code{testwolfcrypt}) and record the DLL SHA-256. Implement the named-pipe transport,
restricted DLL loading (\code{LoadLibraryExW}), Windows service, Windows collectors, and
MSI behind the platform adapters. Seeding uses the same Lightrider callback with
\code{BCryptGenRandom} as the kernel source. The Windows 11 Pro/i7-1260P OE is tested
and awaiting publication on \#4718; until the published security policy lists it,
Windows ships with \code{validation\_status()} reporting \code{pending\_publication} and
no validated-deployment claim.

\section{Manual Two-Host Interoperability Test}\label{app:twohost}

\code{docs/two-server-manual-test.md}. It assigns
\code{168.231.75.64} (\code{srv811871.hstgr.cloud}) as signer/ML-KEM sender and
